# จุดถามสถานะ PWR — สัญญากับระบบวางแผนการบิน

**สถานะ:** เขียนและทดสอบแล้ว · **ยังไม่ deploy** รอเจ้าของงานตั้งความลับและอนุมัติ

---

## ปัญหาที่จุดนี้แก้

ระบบวางแผนการบินรู้ว่าเที่ยวบินมีผู้โดยสารกี่คน ระบบฟอร์มรู้ว่าใครส่งใบมา
ไม่มีฝั่งไหนตอบได้ว่า **"ใครยังไม่กรอก"** เพราะข้อมูลอยู่คนละที่

ผูกกันด้วยกุญแจของฝั่งวางแผนการบิน ไม่ใช่ชื่อ — ชื่อสะกดต่างกันได้ และเป็นข้อมูลส่วนบุคคล

```
ใบ PWR พก ref ของอีกฝั่งเข้ามาทางลิงก์ prefill  →  อีกฝั่งถามกลับด้วย ref เดิม
```

## ทำไมต้องมีชีต `PWR — Index` แยกจาก `PWR — Records`

`Records` เขียนตอนใบ **จบ** เท่านั้น PWR มีสองขั้น (ผู้โดยสารเซ็น แล้ว HT เซ็น)
ช่วงรอ HT ใบอยู่ใน Firestore ที่เดียว ตัวส่งออกมองไม่เห็น

เจ้าของงานตัดสินแล้วว่า **ผู้โดยสารที่เซ็นแล้วขึ้นเครื่องได้ ไม่ต้องรอ HT** แต่บอร์ด
คาสีเหลืองไว้จนกว่า HT จะเซ็น แปลว่า `pending` ไม่ใช่สถานะชั่วคราวที่ผ่านไปไว
มันคือสถานะที่บอร์ดแสดงจริงเป็นชั่วโมงหรือเป็นวัน จุดนี้จึงต้องตอบ `pending` ได้

ชีตนี้เป็นแหล่งข้อมูลที่สอง ซึ่งเพี้ยนจาก Firestore ได้ **ทิศทางที่ยอมให้เพี้ยนคือ
"ยังไม่กรอก" เสมอ** — รายงานว่าเสร็จทั้งที่ยังไม่เสร็จอันตรายกว่ามาก เพราะจะมีคน
ขึ้นเครื่องโดยไม่มีหนังสือสละสิทธิ์

ย้ายไปอ่าน Firestore ตรง ๆ ทีหลังได้โดยไม่เปลี่ยนสัญญานี้

## สัญญา

```
GET <gasUrl>?api=pwr&ref=A1B2C3D4,B2C3D4E5&key=<ความลับ>
```

```json
{ "ok": true, "result": {
    "A1B2C3D4": { "ref":"A1B2C3D4", "tracking":"PWR-20260822-AAAA",
                  "status":"pending",  "submittedAt":"2026-08-22T03:00:00.000Z",
                  "signedAt":null,     "pdfUrl":null },
    "B2C3D4E5": { "ref":"B2C3D4E5", "tracking":"PWR-20260821-BBBB",
                  "status":"complete", "submittedAt":"2026-08-21T02:00:00.000Z",
                  "signedAt":"2026-08-21T09:30:00.000Z",
                  "pdfUrl":"https://drive.google.com/..." },
    "ZZZZZZZZ": { "ref":"ZZZZZZZZ", "status":"none" } } }
```

| ค่า | ความหมาย | บอร์ดฝั่งวางแผนการบิน |
|---|---|---|
| `none` | ยังไม่มีใบที่พก ref นี้ | ยังไม่กรอก |
| `pending` | ผู้โดยสารเซ็นแล้ว รอ HT | ขึ้นบินได้ · คาสีเหลือง |
| `complete` | HT เซ็นแล้ว มี PDF | เขียว |

**`submittedAt` = ผู้โดยสารกดส่ง · `signedAt` = HT เซ็น** — สองตัวนี้คนละเหตุการณ์

**ไม่มีข้อมูลส่วนบุคคลในคำตอบ** ไม่มีชื่อ ไม่มีเลขบัตร ไม่มีอีเมล ไม่มีที่อยู่ ไม่มีลายเซ็น
ฝั่งที่ถามมีรายชื่อผู้โดยสารของตัวเองอยู่แล้ว ส่งกลับไปอีกก็ได้แค่ทำให้ข้อมูลอ่อนไหวอยู่สองที่

### ข้อจำกัด
- ต้องมี `key` ตรงกับ Script Property `PWR_STATUS_KEY` · **ไม่ได้ตั้ง = ปิดสนิท ไม่ใช่เปิดโล่ง**
- ถามได้ครั้งละไม่เกิน **50 ref**
- เรียกจาก **backend เท่านั้น** (`UrlFetchApp`) ถ้าเรียกจากเบราว์เซอร์ ความลับจะอยู่ใน
  bundle แล้วไม่มีความหมาย

---

## ขั้นตอนเปิดใช้งาน (ต้องทำด้วยมือ)

1. เปิด Apps Script → Project Settings → Script Properties
2. เพิ่ม `PWR_STATUS_KEY` = ความลับที่สุ่มมา (แนะนำ 32 ตัวขึ้นไป)
3. deploy เป็น **เวอร์ชันใหม่ของ deployment เดิม** เพื่อให้ URL ไม่เปลี่ยน
4. วางความลับตัวเดียวกันใน Script Properties ของระบบวางแผนการบิน ชื่อ `PWR_STATUS_KEY`

**ความลับต้องไม่ถูกส่งผ่านแชทหรือ commit ลงรีโป** ทั้งสองฝั่งเก็บใน Script Properties
คนที่วางค่าคือเจ้าของงาน ไม่ใช่เอเจนต์

## ทดสอบแล้ว

`/tmp/t_api.js` · `/tmp/t_idx.js` · `/tmp/t_name.js` — 22 กรณี ครอบคลุม

- ยังไม่ตั้งความลับ → ปิดสนิททุกทาง แม้เดา key ถูกก็ไม่ได้
- key ผิด / ไม่ส่ง / ส่งแค่บางส่วนของค่าที่ถูก → ปฏิเสธ
- เกิน 50 ref → ปฏิเสธ · ไม่ส่ง ref → ปฏิเสธ · api อื่น → ปฏิเสธ
- คำตอบไม่มีคำว่า paxName / paxId / paxEmail / paxAddr / Sign
- register ซ้ำไม่เพิ่มแถว · register ทับใบที่จบแล้ว **ไม่ถอยสถานะกลับ**
- ใบที่จบโดยไม่เคย register → ยังบันทึกลงดัชนีได้
