# การบริหารจัดการฟอร์ม (form management)

โจทย์ 6 ข้อ + เพิ่ม/เปิด-ปิดฟอร์ม — เอกสารนี้เป็นการออกแบบก่อนลงมือ
คู่กับ `_SCHEMA.md` ซึ่งว่าด้วย *รูปร่างของฟอร์ม* ส่วนไฟล์นี้ว่าด้วย *วงจรชีวิตของฟอร์ม*

---

## 0. การตัดสินใจตั้งต้น — นิยามฟอร์มย้ายจากไฟล์ไป Firestore

เดิม `formdefs/*.json` อยู่ใน repo แล้วฝังตอน build → **เพิ่มฟอร์มหรือปิดฟอร์มต้อง build + push ทุกครั้ง**
ซึ่งขัดกับข้อ "เพิ่ม form / enable-disable form ได้"

จึงย้ายไป Firestore และให้ไฟล์ JSON ใน repo เป็นเพียง **รูปแบบนำเข้า/สำรอง**

| | เดิม | ใหม่ |
|---|---|---|
| ที่อยู่จริง | ไฟล์ใน repo | `formDefs/{code}` ใน Firestore |
| เพิ่มฟอร์ม | แก้ไฟล์ → build → push | อัปโหลด JSON ที่ `/admin/forms/` |
| เปิด/ปิด | ทำไม่ได้ | สลับสถานะได้ทันที |
| ประวัติเวอร์ชัน | git log | `formDefs/{code}/versions/{defRev}` |

**ข้อแลก** — ต้อง login ถึงจะแก้ได้ และคนแก้ต้องอยู่ใน `staffEmails()`
ส่วน git ยังเก็บสำเนาไว้เป็น backup ผ่านปุ่ม “ดาวน์โหลดทั้งหมด”

## 1. เวอร์ชัน — สองชั้นที่ต้องไม่สับสน

| ชั้น | คืออะไร | เปลี่ยนเมื่อไร |
|---|---|---|
| **Issue / Rev** | เลขของ**เอกสารควบคุม**ตามคู่มือ เช่น `ISSUE 01/REVISION 00` | เมื่อเนื้อหาฟอร์มเปลี่ยนจนต้องแจ้ง CAAT / แก้ LEF |
| **defRev** | เลขรุ่นของ**นิยามในระบบ** (จำนวนเต็ม เพิ่มทีละ 1) | ทุกครั้งที่กด publish ไม่ว่าจะแก้อะไร |

ทำไมต้องมีสองชั้น — แก้ข้อความ hint หรือเพิ่มคำค้นไม่ควรไปแตะเลข Revision ของเอกสารควบคุม
แต่ระบบยังต้องรู้ว่า record ใบนี้กรอกด้วยนิยามรุ่นไหน

**กติกาเหล็ก** — ทุก submission บันทึก `defRev` และ `issueRev` ที่ใช้กรอกจริง
แก้นิยามภายหลัง**ไม่ย้อนไปเปลี่ยนของเก่า** (ข้อกำหนดเอกสารควบคุม)

### การขึ้นเวอร์ชัน

```
แก้ร่าง (draft)      → แก้ได้อิสระ ยังไม่มีผลกับผู้ใช้
publish รุ่นใหม่      → defRev +1  ·  ต้องระบุ "แก้อะไร" และ "เหตุผล"
   ├─ ไม่เปลี่ยนเอกสาร      Issue/Rev คงเดิม
   ├─ แก้ไข (revision)      Rev +1        → ต้องอัปเดต LEF
   └─ ออกฉบับใหม่ (issue)   Issue +1, Rev = 00 → ต้องอัปเดต LEF + แจ้ง Distribution List
```

## 2. Log การแก้ไข

`formDefs/{code}/events/{id}` — **append-only แก้ไม่ได้ ลบไม่ได้**

```jsonc
{
  "at": <timestamp>, "by": "someone@d0507.co.th",
  "action": "created | edited | published | disabled | enabled | imported",
  "fromDefRev": 3, "toDefRev": 4,
  "fromIssueRev": "01/02", "toIssueRev": "01/03",
  "changeNote": "เพิ่มช่องชั่วโมงพักผ่อน 24 ชม. และปรับเกณฑ์คะแนนเป็น 3 ระดับ",
  "reason": "Regulatory | Operational | Clarity | Correction",
  "diff": { "added": ["restHours"], "removed": [], "changed": ["score"] }
}
```

`reason` ใช้ค่าเดียวกับ `SKILL: editor-note` ใน CLAUDE.md เพื่อให้ generate editor note
และ revision log ออกมาได้ตรงรูปแบบที่คู่มือกำหนด

## 3. หน้าตรวจทานก่อนส่ง

ก่อน submit ทุกครั้ง — ไม่ใช่ `confirm()` ธรรมดา แต่เป็นหน้าสรุปที่แสดง:

- ทุกคำตอบที่กรอก จัดกลุ่มตาม section (อ่านอย่างเดียว)
- ค่าที่คำนวณได้ และ gate ที่ทำงานอยู่
- ปลายทาง — จบที่ submit หรือส่งต่อให้ใคร
- คำเตือนว่ากดส่งแล้วแก้เองไม่ได้ ต้องให้เจ้าหน้าที่แก้
- ปุ่ม **กลับไปแก้** / **ยืนยันส่ง**

ทำใน `formkit.js` เป็นขั้นที่ 2 ของการส่ง — ใช้ได้กับทุกฟอร์มโดยไม่ต้องเขียนเพิ่มรายใบ

## 4–6. บันทึกลง Google Sheet และ Drive (PDF)

### ปลายทางสองจังหวะ

| จังหวะ | เงื่อนไข | บันทึกอะไร |
|---|---|---|
| **จบที่ submit** | `route` มีขั้นเดียว | Sheet 1 แถว + PDF ฉบับสมบูรณ์ |
| **จบทั้ง flow** | ผ่านทุกขั้นและลงนามครบ | Sheet 1 แถว + PDF ฉบับสมบูรณ์พร้อมลายเซ็นทุกฝ่าย |

ระหว่างทาง (รออนุมัติ) **ยังไม่เขียนลง Sheet/Drive** — เขียนเมื่อจบเท่านั้น
กันไม่ให้มีเอกสารครึ่ง ๆ กลาง ๆ ปนอยู่ในแฟ้ม

### สถาปัตยกรรมที่เสนอ — Google Apps Script

เว็บนี้เป็น static บน GitHub Pages เขียน Sheets/Drive ตรงจากเบราว์เซอร์ไม่ได้
มีสามทาง:

| ทาง | ต้องมีอะไร | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **Apps Script Web App** ⭐ | บัญชี Google ที่มีอยู่แล้ว | ฟรี · เข้าถึง Sheet/Drive/Docs ได้ตรง · ทำ PDF จาก Google Doc template ได้ | ต้อง deploy สคริปต์แยก |
| Cloud Functions | **Blaze** + service account | อยู่ในระบบเดียวกัน | เสียเงินตามใช้ · ตั้งค่าซับซ้อนกว่า |
| เขียนมือ | — | ไม่ต้องทำอะไร | ไม่ตอบโจทย์ |

**เลือก Apps Script** เพราะได้ PDF ที่หน้าตาตรงฟอร์มจริงด้วย:
อัปโหลด `D-0507-*.docx` ขึ้น Drive แปลงเป็น Google Doc → สคริปต์แทนค่าลง placeholder → export PDF
เป็นวิธีเดียวกับที่วางไว้แต่แรกว่าจะใช้ `.docx` ต้นฉบับเป็นแม่แบบ

### ความปลอดภัยของ endpoint

Apps Script web app ที่เปิดรับ POST จากเว็บสาธารณะ = ใครก็ยิงได้
จึงให้ client แนบ **Firebase ID token** ไปด้วย แล้วสคริปต์ตรวจว่า:

1. token ลงนามโดย Firebase ของโปรเจกต์ `d0507-forms` จริง
2. `aud` = `d0507-forms` และยังไม่หมดอายุ
3. submission id ที่อ้างมีอยู่จริงและสถานะเป็น "จบแล้ว"

นักเรียนที่ล็อกอินแบบ anonymous ก็มี ID token จึงใช้กติกาเดียวกันได้

⚠️ **ยังไม่ทำในรอบนี้** — ต้องได้ชื่อ Sheet ปลายทาง โฟลเดอร์ Drive และแม่แบบเอกสารก่อน

## 7. เพิ่มฟอร์ม / เปิด-ปิด

### สถานะของฟอร์ม

| สถานะ | ในคลังฟอร์ม | เริ่มกรอกใหม่ | ใบที่ค้างอยู่ |
|---|---|---|---|
| `draft` | เห็นเฉพาะเจ้าหน้าที่ ติดป้าย “ร่าง” | ได้ (สำหรับทดสอบ) | — |
| `published` | เห็นตามปกติ | ได้ | เดินต่อได้ |
| `disabled` | ซ่อน | **ไม่ได้** | **เดินต่อได้จนจบ** |

ปิดฟอร์มแล้วใบที่ค้างอยู่ต้องเดินต่อได้จนจบ ไม่งั้นงานค้างกลางทางจะไปต่อไม่ได้

### เพิ่มฟอร์มใหม่ ทำได้ 3 ทาง

1. **อัปโหลด JSON** ตามแบบใน `_SCHEMA.md`
2. **คัดลอกจากฟอร์มที่มีอยู่** แล้วแก้
3. **เริ่มจากแม่แบบเปล่า** (`_TEMPLATE.json`)

ทุกทางเข้า pipeline เดียวกัน: ตรวจตามสเปก → บันทึกเป็น `draft` → publish เมื่อพร้อม

### ด่านตรวจก่อน publish

- `code` ต้องมีใน `forms_register.json`
- `party` ที่อ้างใน section/route ต้องมีจริง
- เงื่อนไข `showIf` / `when` ต้องอ้างฟิลด์ที่มีจริง
- `type` ต้องเป็นชนิดที่รองรับ
- ต้องมี `changeNote` และ `reason`
